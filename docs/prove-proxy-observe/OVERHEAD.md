# Prove Proxy 观测开销与验收记录

记录日期：2026-10-16。本文用于持续记录阻塞观测改造的性能成本、证据和上线判断。

## 当前结论

**启用观测会增加 CPU、内存和日志 I/O 开销；关闭观测也不能承诺严格零开销。实际证明负载的 release A/B 尚未完成，目前没有可信的线上开销百分比。**

有界队列、独立写日志线程和非阻塞投递避免请求直接等待日志写盘，但不能消除 JSON 构造、计时、状态更新以及共享 CPU、内存和磁盘的成本。测试通过说明功能与生命周期符合测试预期，不等于性能已验收。

## 开销来自哪里

| 路径 | 新增工作 | 需要测量的影响 |
|---|---|---|
| 关闭观测 | 中间件包装、开关/context 检查，部分调用层的 guard、计时或装箱 | 相对未改造版本的残余 CPU/延迟开销 |
| 请求和 job 跟踪 | 分配关联上下文、登记和清理活动、更新阶段状态 | CPU/request、活动数与内存 |
| 阶段事件 | 时间戳、JSON 构造、向有界队列投递 | CPU/request、日志字节/request、事件丢失 |
| 日志 writer | 独立线程写 JSONL、轮转 | 磁盘写入量、writer CPU、日志新鲜度 |
| heartbeat / watchdog | Tokio 心跳、独立线程扫描活动和生成快照 | 固定背景成本、扫描成本、快照完整性 |
| 外部采样与 role 探针 | 读取 proc/cgroup、可选 nvidia-smi、定时 RPC | 额外进程 CPU、I/O、探针对服务的影响 |

plonky2 phase hook 在未安装 callback 时不创建日志、不读取时钟、不分配 guard；这只描述该 hook，不能外推为整个关闭路径零开销。Hook 不传播到每个 Rayon worker，也没有为每个 FFT butterfly 或 Poseidon permutation 写日志。

外部采样器和 role 探针需要单独启动，不会因设置 Observer 环境变量而自动运行。测试时应固定它们的配置，必要时再单独测其成本。

## 当前开关和资源边界

`PSY_PROVE_OBSERVE_DIR` 未设置时关闭 Observer；设置有效可写目录后启用。空值或无效目录会导致启动失败，不会默默降级为关闭。

| 项目 | 当前默认值 | 边界含义 |
|---|---:|---|
| 跟踪活动容量 | 1,024 | request/job/build 活动数；不是 1,024 个独立请求 |
| 事件队列容量 | 4,096 | 队列条目数；不是明确的总字节/RSS 上限 |
| 日志轮转 | 4 个文件，每个 16 MiB | 正常情况下约 64 MiB 留存容量；不是写入带宽上限 |
| heartbeat | 1 秒 | Tokio runtime 进展信号 |
| watchdog | 5 秒 | 独立线程扫描跟踪槽位，输出最老的至多 16 个活动 |

以上容量目前是代码默认配置，不应当当成已经暴露的环境变量。普通阶段事件当前没有抽样开关；不是只记录慢请求。活动和日志有界也不代表整个证明进程的 RSS 有界。

日志过载时会丢事件，慢请求和错误事件也不保证完整。分析必须同时读取 `dropped_events`、`tracker_overflow`、`snapshot_skipped`、`state_skipped` 和 `writer_errors`，并通过外部 `observer_log_age_s` 检查日志是否停更。缺失事件不能解释为对应阶段没有执行。

## 已有实测：第一阶段 debug 中间件探针

来源：[VALIDATION.md](VALIDATION.md)。原始日志在工作区 `evidence/middleware-overhead-debug.log` 和 `evidence/middleware-paced-debug.log`。

条件：debug 构建、本机 loopback、真实 jsonrpsee/HTTP、8 并发；处理器返回固定值，包含 blocking job 和模拟 build。**不生成真实证明，也不包含第二阶段新增的全部内部阶段事件。**

无限速突发，每轮 2,000 请求，off/on/on/off：

| 观测 | 总时间 ms | dropped_events |
|---|---:|---:|
| off | 307.8 | — |
| on | 471.9 | 14,660 |
| on | 585.0 | 11,930 |
| off | 390.5 | — |

这证明极短请求突发下存在明显成本和队列饱和，不能声称观测免费。不能把这个耗时比例套用到秒级证明。突发测试发生过轮转，最终保留文件大小不能当成总日志生成量。

定速约 40 请求/秒，每轮 400 请求，off/on/on/off：

| 观测 | 总时间 ms | 日志字节 | 丢事件 / 跟踪溢出 |
|---|---:|---:|---:|
| off | 10,056.6 | 0 | — |
| on | 10,056.3 | 1,390,322 | 0 / 0 |
| on | 10,059.2 | 1,390,285 | 0 / 0 |
| off | 10,060.4 | 0 | — |

末尾 inflight 为 0，writer_errors 为 0。这说明该 mock 速率下日志能够持续写入。定速等待主导总时间，不能据此得出“没有性能影响”。

该负载约产生 3.5 KB/request，按 64 MiB 容量估算约保留 8 分钟。真实证明阶段数更多，第二阶段还增加了内部事件；**这两个估算都不能直接用于当前版本的生产日志规划**。

## 下一轮测量方案

建议设置三组，避免遗漏关闭观测仍然存在的成本：

| 组别 | 版本/配置 | 回答的问题 |
|---|---|---|
| A | 兼容的观测改造前版本，保留相同 GPU/CPU 优化 | 原始基线 |
| B | 候选 release 二进制，Observer 关闭 | A/B 衡量编译进观测代码后的残余成本 |
| C | 与 B 完全相同的二进制，Observer 开启 | B/C 衡量启用观测的增量成本 |

1. 固定源提交、依赖、二进制 hash、编译选项、CPU 指令集、GPU 开关、lane/slot/内存预算；A 与 B 的源差异必须可审核。
2. 使用同一批脱敏真实请求，固定 mix、请求顺序和并发。区分 user/system，不把两者结果混合；冷缓存与热缓存分开测。
3. 在无其他压测的机器上交替运行，各组至少两次；覆盖并发 1 和部署代表性并发。记录背景负载，出现干扰的轮次单独标记。
4. 性能轮使用生产证明配置。确定性 PoW/random、逐证明额外验证和故障注入只用于独立正确性轮，不能混入性能比较。
5. 比较总吞吐、分方法 p50/p95/p99、CPU 秒/成功请求、RSS/cgroup 峰值和回落、日志生成速率及丢失计数。外部采样在各组保持一致，包含 observer/writer 的服务总 CPU。
6. 做同进程连续多轮，检查活动是否清零、RSS 是否稳定、日志是否正常轮转。额外模拟日志队列拥塞/慢盘，检查业务活性和观测缺口，避免把丢日志误认为低开销。

吞吐损失按 `1 - C吞吐/B吞吐` 计算，CPU/request 增量按 `C/B - 1` 计算。A/B 同理。固定速率测试用于日志可持续性；最大吞吐测试用于容量影响，二者分别报告。

性能验收阈值尚未确定，不能预先宣称“低于 1%”或“可忽略”。先取得重复测量的波动范围，再决定常驻开关、日志粒度和是否需要新增抽样策略。

## 上线边界

当前只完成本地开发和上述验证。后续先完成 release 回放与开销测量，再安排单 backend 灰度，观察业务延迟与日志覆盖。若开启后的成本不可接受，可在受控重启时移除 `PSY_PROVE_OBSERVE_DIR` 关闭观测；关闭仍保留候选代码的残余成本，需要恢复旧二进制才能回到 A 组状态。当前没有运行时热关闭保证。
